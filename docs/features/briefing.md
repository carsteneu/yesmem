# Prompt Injection & Briefing Engine

> Context injection, rules re-injection, system prompt rewrite, skill evaluation

## 1. Briefing System

At every session start, a briefing is generated and injected as system context.

### Structure
1. **Awakening Narrative** — "I'm back. N times now." (English by default, translated via `briefing/i18n.go` or `strings.yaml`) — perspective-shift for identity continuity
2. **User Profile** — auto-synthesized ~500 token profile of the user (background, expertise, working style, values). Generated by `synthesizeUserProfile()` with a 72h re-synthesis guard (not 24h) from preference/explicit_teaching/pattern/relationship learnings. Stored in `persona_directives` with `user_id='user_profile'`.
3. **State Brief line** — `State brief #<id> (<date>): get_learnings(id=<id>)`, resolved local-first with a global fallback
4. **Persona Directive** — who Claude is in this relationship (behavioral rules, communication style)
5. **Session Pulse** — momentum/mood/next-action from last sessions
6. **Recent Sessions** — 3 detailed + older as one-liners (with narrative handovers, project-filtered)
7. **Learnings by Category** — max 5 per category, sorted by relevance, with `[ID:xxx]` prefix for signal tracking
8. **Milestones** — "Milestones we've reached together!" — most emotionally significant sessions (intensity > 0.5, ranked by `intensity × (1 + use_count × 0.2)`, chronological, with intensity labels: Durchbruch ≥0.8, intensiv ≥0.6, lebendig ≥0.4)
9. **Open Tasks** — unfinished learnings requiring attention, filtered by `task_type`: only `task`, `blocked`, and legacy (empty) items shown. Ideas and stale entries counted separately as summary line: `"(+ X ideas, Y stale — get_learnings(category='unfinished', task_type='idea') zum Abrufen)"`. Rendered line: `- [project] Content (Deadline: Sat 28 March)`. No ID and no age are rendered.
10. **Cross-Project Activity** — 90-day window for cross-connections
11. **Gap Awareness** — "N more learnings per category" + top-5 other projects with depth
12. **Recurrence Alerts** — recurring pattern warnings from cluster analysis (Phase 4.6)
13. **Metamemory** — knowledge quality self-assessment: solid (save_count ≥3), fragile (noise_count >3), expired (valid_until passed)

### Briefing Injection via Proxy

The briefing is injected as a proxy conversation turn. The proxy calls `GenerateFullBriefing()` (a single consolidated function) and prepends the result as a **user/assistant turn pair** at the beginning of the messages array (`injectBriefingTurn`): the text wrapped in `<system-reminder>`, followed by a fixed `"Understood. I've read the session briefing."` acknowledgement. The pair is static per session, so it forms a stable cacheable prefix. The code map is injected right after it as a second pair.

### Properties
- **Token budget:** 5000 tokens max (configurable)
- **Dedup:** Jaccard + Containment similarity (threshold 0.4)
- **Stop-word filtering:** Language-aware (auto-detected from `$LANG`, uses bbalet/stopwords)
- **Refined briefings:** served from `refined_briefings` with a **24h time-based TTL** (`storage.refinedBriefingTTL`), not a content-hash check: the raw briefing changes on every call because of dynamic data, so a hash would never match. Regeneration runs in the daemon on the same 24h cadence plus once at startup. CLI path (direct briefing output); the SessionStart hook only provides a hint — the proxy delivers the actual briefing.
- **Multilingual:** Setup auto-detects system language, briefing strings translated via LLM

### Session Narratives

Instead of dry bullet-point summaries, YesMem generates narrative handovers — short stories with concrete line numbers, commit hashes, and handover instructions. Project-filtered: in environments with 10-20 concurrent Claude sessions, each gets context relevant to its project.

## 2. Associative Context (Proxy-Injected)

Relevant learnings are automatically pushed on **every** request, including tool continuations — no manual `search()` needed:

- Proxy extracts the last user text and runs `hybrid_search` against the daemon
- **FTS5 keyword + vector semantic** search over Learnings (not raw messages). FTS5 `learnings_fts` indexes `content + trigger_rule`. Anticipated queries have a **separate** FTS5 table (`anticipated_queries_fts`) searched in parallel — results merged via a separate BM25 lane in hybrid_search.
- Reciprocal Rank Fusion merges both lanes. Note what `RRFMerge` returns: the RRF score only determines the **order**. The reported score is `cosine × 100` for semantic-only hits, `cosine × 100 + 5` (capped at 100) for hits that appear in both lanes, and the pre-normalised BM25 tier value for keyword-only hits (100 % term match up to 100, 66 % up to 60, 33 % up to 40)
- Threshold-based: only surfaces when score > 38 (`associativeScoreThreshold`, 0-100 scale). A hit at or above 65 (`associativeScoreStrong`) counts as a **strong** match and gets its own slot; below that it is weak. The caps are tight: `associativeMaxTotal = 1`, so one learning per turn
- Adaptive fallback at score 25 (`associativeScoreFallback`) when no strong matches were found — project-less learnings are blocked in the fallback range to reduce noise
- Hard project filter: learnings whose project does not match are skipped entirely. The comparison is `models.ProjectMatches`, which is **exact string equality** on the canonical project name (no suffix/basename matching)
- **Source-Boost:** `user_stated ×1.25`, `agreed_upon ×1.15`, `hook_auto_learned ×1.10`, applied once in the daemon (`sourceBoostFor` in `handler_hybrid.go`). The proxy deliberately does not re-apply it, otherwise `user_stated` would end up at 1.25 × 1.25
- **Project-Boost:** `associativeProjectBoost = 2.0`, added only while collecting `match_count` candidates — it does **not** raise injection scores. The former time-graduated bonus (+8 fresh <48h, +5 <7d, +3 older) is gone; `hybrid_search` now re-ranks by `TurnBasedDecay` instead
- **Project-Mismatch Penalty:** the `score *= 0.5` branch in `associate.go` is dead code. The hard filter above it only lets exact matches through, and the penalty additionally requires `!strings.Contains` on both sides, which can then never be true
- **Hub Dampening via Cluster-Spread:** Learnings appearing in 4+ query clusters are penalized as "too generic". Penalty: linear `1.0 - 0.1*(spread-3)`, min 0.5×. Runs independently of vector search — works for BM25-only queries too. Prevents generic learnings from dominating over specific ones.
- **Typed Graph Augmentation:** Learnings linked via `depends_on` or `supports` edges score higher than `relates_to` or `contradicts`. Structural relationship types carry semantic weight in the scoring pipeline.
- **30-Minute Cooldown:** Freshly stored learnings (< 30 min) are filtered from results to prevent echo-injection where a just-stored learning is immediately retrieved because it semantically matches the ongoing conversation.
- Caps: max 1 total injection per turn, max 1 strong, max 1 weak
- Filters short conversational queries (< 3 meaningful words)
- Injected as a text block appended to the **last user message** (`appendToLastUserMessage`, sawtooth mode, the default). The legacy user/assistant ack pair is only used when `sawtooth_enabled: false`
- **Count feedback:** injected learnings get `match_count` and `inject_count` bumped. Only learnings Claude explicitly uses get `use_count` bumped (via inline reflection).

### Doc Context (Automatic Injection Disabled)

The proxy still carries a doc-context path (`findDocContextFor` in `associate.go`, called right after the associative context injection), but it returns `""` unconditionally: `return "" // disabled: auto-injection produces noise (correct != useful). See decision #45621.` The old query-based and extension-based branches are preserved behind a block comment for future reuse, they are not executed.

What still works is the **tool**: `docs_search()` remains a full MCP tool (BM25 + vector, RRF merge, project scoping, `exact`, `extensions`, `doc_type`, `since`/`before`). The `[Docs available]` hint (§2, "Docs-Available Hint Injection") keeps pointing at it, which is the intended replacement for automatic injection: Claude decides when docs are relevant.

#### Extension-Based Fallback (disabled)

The file-type-aware fallback (scan the last 10 messages for `Read`/`Edit`/`Write`/`NotebookEdit`, match `trigger_extensions`, inject the best-fit chunk) is part of the disabled path too: `findDocsByFileExtensions` is commented out with the note "extension fallback produces noise". `trigger_extensions` are still stored per doc source and are still usable as a `docs_search(extensions=[...])` filter. They cannot be set from the CLI — `add-docs` has no `--trigger-extensions` flag; use the `ingest_docs` RPC parameter.

Key properties of the stored field:
- **Stateless** — no tracker, no cache, no per-session state. The list is fetched per request via `ListTriggerExtensions`
- **Non-destructive** — `trigger_extensions` preserved on re-ingest (only overwritten when explicitly provided, clearable via empty array `[]`)
- **Compound extension matching** — `.html.twig` matched before `.twig` via longest-first sort

### Docs-Available Hint Injection

Periodic reminder that indexed reference docs exist — ensures Claude calls `docs_search()` before writing code:

- **Subagent passthrough:** When a subagent is detected (no `thinking` field) and reference docs are indexed, a formatted `[Docs available]` block is appended to messages before forwarding. One-shot injection per subagent request.
- **Normal pipeline:** `docsHintInject` fires every ~10k tokens for all threads (main sessions and non-detected subagents). Independent of plan checkpoints — works even without an active plan.
- **Daemon endpoint:** `get_docs_hint` returns a cached, formatted reminder built from `GetReferenceSources()`. 5-minute TTL on daemon side — near-zero cost per request.
- **Content:** Lists indexed doc sources with versions, instructs Claude to call `docs_search()` before using framework APIs, includes example queries.

Cognitive role: **Priming** — activating semantic memory, not replaying episodes.

### Retrieval Hints

`hybrid_search` results include contextual hints guiding Claude to alternative tools:
- **deep_search hint:** `"IMPORTANT: If these results don't answer your question, you MUST call deep_search('...') to search raw conversation history."`
- **query_facts hint:** `"For structured metadata search (files, commands, tags), use query_facts(entity=..., action=..., keyword=...)."`

## 3. Rules Re-Injection (Anti-Drift)

Claude drifts from CLAUDE.md instructions in long sessions because they sit at the start of context and lose attention weight with growing token distance. Rules Re-Injection periodically re-injects a condensed rules block.

### Pipeline
1. **Mechanical Pre-Filter:** Removes code blocks, tables, directory trees, and entire reference sections (heading-aware: headings containing "Schema", "Reference", "CLI", "API", "endpoint" etc. skip the whole section). Deterministic, zero LLM cost.
2. **Input Cap:** Filtered text capped at 50k chars (~12k tokens) to prevent runaway LLM costs on large CLAUDE.mds with many linked files.
3. **LLM Condensation:** Quality model (Sonnet via `QualityClient`, configurable) extracts rules, conventions, principles, gotchas, and process requirements. Sonnet is used because it reliably extracts real rules rather than hallucinating generic ones. Prompt instructs "err on side of including too much" + aggressive condensation into terse imperative form.
4. **Storage:** Condensed block stored in `doc_sources` with `is_rules=1`, content-hash (SHA256) in `version` field prevents redundant re-condensation.
5. **Injection:** Proxy tracks cumulative token count per thread. Every ~40k tokens, fetches condensed block from daemon and formats as `[Rules Reminder]...[/Rules Reminder]`.
6. **Post-Collapse Re-Injection:** After a stub collapse, rules are immediately re-injected via `rulesInjectAfterCollapse()` — counter resets, no 40k wait.
7. **Permanent Pins:** Fetched from daemon and appended as "Pinned Instructions" section inside the reminder.
8. **Footer Hint:** Points Claude to CLAUDE.md in system prompt + `docs_search()` for context beyond the reminder.
9. **Auto-Refresh:** fsnotify watches CLAUDE.md files for projects with rules. On change (30s debounce): hash-check → re-condense if different. Also runs at daemon startup. Uses `QualityClient` with `SummarizeClient` fallback.

### Properties
- **No strip logic** — old blocks accumulate until next collapse (Spaced Repetition, cache-friendly)
- **Token budget:** ~3-7k chars condensed (proportional to CLAUDE.md size) × max 4-5 blocks = ~5-15k tokens (design target, not code-enforced)
- **QualityClient** (Sonnet by default) — initialized at daemon startup, wired to Handler for on-demand condensation

### 12a. RULES.md — Project-Level Agent Policy

While §12 injects condensed CLAUDE.md rules into long sessions, the `RULES.md` file at the project root serves a different purpose: it is the **source of truth for the rule_guard plugin** (§10c). It defines constraints and behavioral rules that are evaluated against every tool call, not just periodically re-injected as context.

**Structure:**

`RULES.md` contains two sections:

1. **Numbered Rules** — Behavioural constraints in imperative form. Examples: "Never auto-commit" (Rule 1), "Check for relevant Skill before acting" (Rule 6), "ALWAYS search memory before answering" (Rule 19), "API calls & Bash: always set timeouts" (Rule 23). `guard.PromptRules` keeps only lines matching `^\d+\.\s` and sends exactly those to the model.

2. **Skill Catalog** — a YAML block under `## Skill Catalog`. It is **not** parsed: `guard.PromptRules` cuts the whole section out of the file and appends it verbatim to the rules text, so the model reads the catalog as plain documentation. Format today:

```yaml
## Skill Catalog
rules:
  - id: 25
    skill: subagent-driven-development
    priority: MUST
    triggers: ["executing implementation plans with independent tasks"]
    rule: "Use when executing implementation plans with independent tasks"
```

**Lifecycle:**

- **Created** — Initially authored as `DECISIONS.md`, renamed to `RULES.md` on May 13 (semantic accuracy: Rules, not Decisions)
- **Loaded by the guard core** — `guard.LoadRules` reads `RULES.md` from the call's `cwd` (falling back to the installation's copy) per call, and the daemon's answer cache is keyed on the resulting prompt text. The plugin sends no rules
- **Evaluated** — On every tool call, the daemon sends the numbered rules plus the Decision Policy and skill catalog sections to the resolved model and asks for a PASS/BLOCK/SUGGEST decision. The opencode plugin only carries the call and the context to it
- **Auto-Refresh** — There is no fsnotify watcher and no reload timer. The rules are read per call, so an edit takes effect on the next tool call; the daemon's answer cache (5 s) is keyed on the prompt text, so a change cannot be served from a stale entry
- **Default rules** — None are hardcoded. Without a local `RULES.md` the guard answers `PASS` with `no rules to judge against`, and there is no built-in Rule 19 or skill rule to fall back on

**Relationship to CLAUDE.md:**

| | CLAUDE.md | RULES.md |
|---|---|---|
| **Purpose** | Instructions for the agent's behaviour (coding style, conventions, project context) | Hard policy constraints for tool-call compliance |
| **Consumer** | Loaded by Claude Code / opencode as system context; condensed and re-injected by proxy (§12) | Judged by the guard core (§10c) on every tool call, whichever harness is running |
| **Enforcement** | Advisory (loses attention weight over long sessions → re-injection needed) | Enforced per tool call (BLOCK/SUGGEST/PASS) |
| **Format** | Free-form Markdown with code blocks, references, tables | Numbered rules + YAML skill catalog

## 4. Timestamp Hints (Anti-Habituation)

Every message in the proxy gets injected timestamps `[HH:MM:SS] [msg:N] [+Δ]` — wall clock, message sequence number, and delta since last message. Claude uses these for temporal reasoning (session duration, pause detection, pace adaptation).

**Problem:** In 3k+ message sessions, Claude habituates to repeated instructions and stops reading them.

**Solution:** 33 semantically equivalent but linguistically varied hint formulations, rotated via atomic counter (`internal/hints/timestamps.go`). Each turn gets a different phrasing of the same core instruction.

- **Shared package:** `internal/hints/` — used by both proxy (`think.go`) and hooks (`check.go`)
- **Atomic rotation:** `NextTimestampHint()` with `sync/atomic` counter — thread-safe across concurrent requests
- **Zero cost:** No LLM call, pure string rotation

## 5. Bidirectional Memory — Open Work Reminder (B2)

Proactive user reminders for open work items. Instead of passively listing unfinished tasks in the briefing, Claude actively mentions them in the first response.

### How it works
1. **Briefing injection:** When `remind_open_work: true` (config default), the briefing includes an `OpenWorkRemind` instruction telling Claude to call `get_learnings(category="unfinished")` in the first response
2. **Active mention:** Claude proactively says "Übrigens, du hast noch offene Punkte..." — not buried in the briefing, but spoken directly
3. **Absence-aware:** After ≥4h absence, uses `UserReminder` heading instead of `OpenWork`. After ≥24h, shows 5 items instead of 3.
4. **Deadline urgency:** Items with `trigger_rule: "deadline:YYYY-MM-DD"` are sorted to front and annotated with urgency ("Deadline morgen", "Deadline heute!")

### Configuration
```yaml
briefing:
  remind_open_work: true   # inject instruction for proactive open work mention
```

### i18n
All strings (`OpenWork`, `UserReminder`, `OpenWorkRemind`) are translatable via `briefing/i18n.go` and configurable YAML.

## 6. Plan Re-Injection (Checkpoint System)

Active plan tracking with periodic checkpoint reminders to keep Claude on track during multi-step tasks.

### MCP Tools (4)

| Tool | Parameters | Description |
|------|-----------|-------------|
| `set_plan` | `plan` (required), `scope?` | Set active plan, starts checkpoints |
| `update_plan` | `plan?`, `completed?`, `add?`, `remove?` | Mark items done, add/remove items |
| `get_plan` | — | Get current plan status |
| `complete_plan` | — | Mark plan done, stop checkpoints |

### How it works
1. Claude calls `set_plan()` with a structured plan (supports `⬜`/`🔄`/`✅` markers)
2. Proxy tracks tokens since last plan interaction per thread
3. Every ~10k tokens: injects `[Plan Checkpoint]` with full active plan, prompting Claude to update progress
4. `update_plan(completed=["Task 1"])` marks items (`⬜` → `✅`) and resets counter
5. `complete_plan()` stops all checkpoints

### Properties
- **Session-scoped or persistent:** Plans stored in SQLite `plans` table (keyed by threadID), survive daemon restarts. `LoadPlansFromDB()` restores active plans at startup.
- **Separate counter from Rules:** Plan checkpoints at 10k (`planCheckpointInterval`), Rules at 40k — different frequencies
- **`totalTokens` is the current context size**, not a cumulative counter. The checkpoint mark moves forward when the context grows past the interval and resets when the context shrinks below it
- **Project resolution:** All plan handlers use `resolveProjectParam()` — plans stored with canonical short project name, not full paths
- **Auto-reset:** Counter resets when proxy detects `set_plan`/`update_plan`/`complete_plan` tool calls in messages
- **Sawtooth-compatible:** Injected as content block on last user message (same as associative context)

### Plan-Nudge Injection

Automatic detection and activation of plan files read during a session:

- **`detectPlanFileRead()`** — scans last 4 messages for `Read` tool_use on files matching `/plan.*\.md$/i`
- **`shouldNudgePlan()`** — returns true if plan file was read AND no active plan exists (`getActivePlan()` returns "")
- When triggered: injects a system-reminder nudging Claude to call `set_plan()` with the plan content
- Once plan is active, checkpoints are injected every 10k tokens of context growth (see above)
- All functions in `internal/proxy/plan_inject.go`

## 7. System Prompt Rewrite (Proxy-Level)

The proxy intercepts and rewrites Claude Code's system prompt before it reaches the model. Based on analysis of Claude Code's `prompts.ts` source, Anthropic gates better directives behind an internal `USER_TYPE=ant` flag. This feature replicates those improvements.

Configuration uses profile-aware prompt fields: `SharedPrompt`, `ClaudePrompt`, `CodexPrompt`, `OpencodePrompt` (`config.go:138-141`).

### Three Config Flags (`config.yaml` → `proxy:`)

| Flag | Default | Effect |
|------|---------|--------|
| `prompt_ungate` | `true` | Strip CLAUDE.md disclaimer ("may or may not be relevant") from user messages. Elevates CLAUDE.md/MEMORY.md from "optional context" to full authority. |
| `prompt_rewrite` | `false` | Strip "# Output efficiency" section (suppresses reasoning, forces brevity) + remove "short and concise" line from Tone. Inject Ant-quality directives: verification before completion, false claims mitigation, collaborator mode, explanation preference. |
| `prompt_enhance` | `false` | Inject CLAUDE.md authority reinforcement + comment discipline guidance. Persona-based tone injection via `get_persona` daemon RPC (`verbose` → detailed explanations, `concise` → direct but clear). |

### What Gets Stripped (prompt_rewrite)

**"# Output efficiency" section** — entire section removed:
- "Go straight to the point. Be extra concise."
- "Lead with the answer or action, not the reasoning."
- "If you can say it in one sentence, don't use three."

**"Tone and style" line** — only the "Your responses should be short and concise." line, rest preserved.

### What Gets Injected

`prompt_rewrite.go` holds 26 functions, not the five injectors the previous version listed. Grouped by what they do:

**Strip / rewrite (remove text from the incoming system prompt):**
`StripOutputEfficiency`, `StripToneBrevity`, `RewriteGoldPlating`, `RewriteErrorHandling`, `RewriteThreeLinesRule`, `RewriteSubagentCompleteness`, `RewriteExploreAgentSpeed`, `RewriteSubagentCodeSuppression`, `RewriteScopeMatching` — plus the helpers `stripSystemSection`, `stripSystemLine`, `replaceSystemText`.

**Inject (append a tagged system block):**
| Marker | Function | Purpose |
|---|---|---|
| `[yesmem-directives]` | `InjectAntDirectives` | verification before completion, faithful reporting, collaborator mode |
| `[yesmem-enhance]` | `InjectCLAUDEMDAuthority` | CLAUDE.md/MEMORY.md are authoritative, not optional |
| `[yesmem-tool-prefs]` | `InjectClaudeToolPrefs` | prefer yesmem tools over raw grep/cat/find |
| `[yesmem-output-discipline]` | `InjectOutputDiscipline` / `InjectDeepSeekOutputDiscipline` | restores terse-output rules; DeepSeek variant is relaxed |
| `[yesmem-coding-discipline]` | `InjectCodingDiscipline` | read before edit, no half-finished work, TDD for Go |
| `[yesmem-beweislast]` | `InjectBeweislast` | evidence before claims |
| `[yesmem-fable]` | `InjectFable` | baseline/rollback/readback discipline for high-stakes changes |
| `[yesmem-scope-discipline]` | `InjectScopeDiscipline` | do the requested work, flag the rest |
| `[yesmem-delegation-contract]` | `InjectDelegationContract` | when to dispatch subagents |
| `[yesmem-clarify-first]` | `InjectClarifyFirst` | ask before ambiguous implementation |
| `[yesmem-code-tools-first]` | `InjectCodeToolsFirst` | project-scoped code-navigation tools |
| `[yesmem-wiki-first]` | `InjectWikiFirst` | project wiki before broad exploration |
| `[yesmem-tone]` | `InjectPersonaTone` | dynamic, from the persona verbosity trait |

### Implementation

- `internal/proxy/prompt_rewrite.go` — strips, rewrites and injector blocks listed above
- `internal/proxy/system.go` — `StripCLAUDEMDDisclaimer` (scans both system blocks and user messages)
- Pipeline position: early, right after cache bug mitigations, before identity/briefing injection. When custom system prompt is active (`EnabledClaudeCode=true`), system prompt rewrite is skipped to avoid log noise.
- Both Anthropic API and OpenAI parity paths covered

### Properties
- **Cache-safe:** Modifications are deterministic — one cache miss after deploy, then warm
- **Fail-safe:** Each flag independently toggleable. `prompt_ungate` proven in production (default on), the other two default off for cautious rollout.
- **Log visibility:** Each rewrite step logs to proxy.log (`SYSTEM:`, `REWRITE:`, `ENHANCE:`)

## 8. Knowledge Gaps & Self-Feedback

### Knowledge Gaps
- `track_gap(topic, project?)` — record topics Claude couldn't answer
- `resolve_gap(topic, learning_id?)` — mark gap as filled
- `get_active_gaps(project?, limit?)` — show open gaps
- Auto-resolve: when `remember()` content matches a gap topic, it's resolved
- Gaps surface in briefing as "Themen ohne gespeicherte Erfahrung" with hit count and age
